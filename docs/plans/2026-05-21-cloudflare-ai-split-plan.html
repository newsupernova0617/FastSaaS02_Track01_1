Cloudflare / AI 분리 계획

Cloudflare Workers는 일반 API를 유지하고, AI 관련 API는 별도 VPS 서비스로 분리하는 운영 계획

현재 문제는 Cloudflare 환경에서 특정 이슈로 외부 AI API 통신이 안정적으로 되지 않는다는 점입니다. 따라서 백엔드 전체를 Workers에서 내리는 대신, 일반 API는 Workers에 남기고 AI 의존 경로만 별도 VPS 서비스로 분리하는 2계층 구조를 목표로 합니다.

기준 문제
Workers ↔ AI API 통신 실패
유지 대상
인증 / CRUD / 일반 조회 API
분리 대상
LLM 호출 / AI 리포트 / AI 채팅
목표 구조
Workers + AI VPS Hybrid

핵심 원칙

이번 계획은 인프라를 전면 교체하는 것이 아니라, 장애 원인이 있는 구간만 분리해서 리스크를 줄이는 방향입니다.

원칙 1
분리 최소화

AI 호출이 필요한 경로만 VPS로 분리

원칙 2
API 경계 명확화

Workers에서 프록시할 라우트를 명시적으로 제한

원칙 3
동일 비즈니스 로직

가능하면 공용 서비스/스키마를 재사용

원칙 4
운영 관측성 확보

Workers와 VPS 로그/에러를 분리 추적

권장 아키텍처

Cloudflare는 사용자 진입점과 일반 API를 담당하고, AI 연산만 VPS로 보냅니다.

Cloudflare Workers에 남길 것

  • JWT 인증 및 사용자 식별
  • 일반 CRUD API: 거래, 사용자, 노트, 연락 요청 등
  • AI 비의존 조회 API
  • CORS, 기본 로깅, rate limit 1차 방어
  • AI 전용 라우트에 대한 프록시/게이트웨이 역할
→

VPS로 분리할 것

  • LLM provider 호출
  • 세션 메시지 처리 중 AI 파싱 경로
  • 리포트 생성 / 요약 생성
  • RAG / vectorize / context enrichment
  • AI 장애 대응용 재시도, timeout, provider fallback

분리 대상 API

우선순위는 “AI를 직접 호출하거나 AI 결과에 강하게 의존하는 라우트”입니다.

1차 분리 대상

  • /api/ai/*
  • POST /api/sessions/:id/messages
  • POST /api/app/chat
  • POST /api/app/push/reply

2차 분리 대상

  • /api/reports/generate
  • /api/reports/current
  • /api/app/reports/generate
  • /api/app/reports/current

Workers 유지 대상

  • /api/transactions
  • /api/users
  • /api/contact-requests
  • /api/notes
  • 기타 AI 비의존 API

권장 요청 흐름

프론트는 여전히 Workers만 바라보게 하고, Workers가 내부적으로 AI VPS에 위임하는 구조가 운영상 가장 단순합니다.

프론트엔드

VITE_API_BASE_URL 은 계속 Cloudflare 엔드포인트를 사용합니다.

Workers 게이트웨이

인증, 기본 검증, 공통 헤더 처리 후 AI 라우트면 내부 프록시를 수행합니다.

AI VPS

실제 LLM 호출, AI 리포트 생성, 세션 메시지 처리, fallback 로직을 담당합니다.

단계별 실행 계획

한 번에 완전 분리하지 말고, 장애 영향이 큰 경로부터 순서대로 잘라내는 것이 맞습니다.

1

AI 경로 식별

현재 라우트 중 LLM 호출, 리포트 생성, vectorize 호출이 실제로 어디서 일어나는지 표로 고정합니다.

선행 작업
2

AI 전용 VPS 앱 구성

공용 서비스 코드를 재사용하되, VPS 엔트리에서 AI 관련 라우트만 우선 실행 가능하게 분리합니다.

핵심 작업
3

Workers 프록시 추가

Cloudflare `backend`에서 AI 라우트만 `AI_API_BASE_URL` 로 프록시하는 분기 로직을 넣습니다.

핵심 작업
4

인증 전달 방식 고정

JWT 원문을 VPS로 그대로 전달할지, Workers에서 검증 후 내부 서명 헤더로 전달할지 결정합니다.

보안 결정 필요
5

로그 / 모니터링 분리

Workers 에러와 VPS AI 에러를 분리해서 수집하고, 프록시 latency도 추적합니다.

운영 필수
6

점진 전환

세션 메시지와 리포트부터 먼저 옮기고, 이후 필요 시 `/api/ai/*` 의 레거시 경로를 정리합니다.

권장 방식

설계 결정 포인트

구현 전에 아래 판단은 확정해야 합니다. 이 부분이 애매하면 나중에 구조가 다시 흔들립니다.

인증 전달

  • 옵션 A: 사용자 JWT를 VPS로 그대로 전달
  • 옵션 B: Workers가 검증 후 내부용 서명 헤더 전달
  • 권장: 내부용 서명 헤더가 더 안전함

DB 접근

  • Workers와 VPS가 같은 Turso DB를 직접 사용
  • 또는 AI VPS만 DB write를 담당
  • 권장: 초기에는 같은 DB 접근으로 단순화

공용 코드 위치

  • 라우트/서비스를 monorepo 공용 레이어로 유지
  • Workers 엔트리와 VPS 엔트리만 분리
  • 권장: 비즈니스 로직 중복 금지

리스크와 대응

이 구조는 현실적이지만, 프록시가 늘어나는 만큼 운영 리스크도 같이 관리해야 합니다.

리스크

  • 프록시 hop 증가로 응답 지연 발생
  • Workers 성공, VPS 실패 같은 부분 장애 가능
  • 인증 전달 설계가 약하면 내부 API 노출 위험

대응

  • AI VPS timeout / retry / circuit breaker 적용
  • 프록시 대상 라우트 최소화
  • 내부 서명 검증과 IP 제한 또는 zero-trust 적용

운영 지표

  • Workers → VPS 프록시 성공률
  • AI provider 응답 시간과 실패율
  • 세션 메시지/리포트 라우트별 P95 latency

권장 결론

현재 상황에서는 전체 백엔드를 VPS로 되돌리기보다, AI 관련 API만 별도 VPS 서비스로 분리하는 하이브리드 구조가 가장 현실적입니다.

왜 이 방향인가

문제가 있는 구간만 우회하므로 변경 범위가 작고, Workers의 배포/엣지 장점도 유지할 수 있습니다.

처음 옮길 것

POST /api/sessions/:id/messages 와 리포트 생성 경로부터 먼저 분리하는 것이 효과 대비 리스크가 낮습니다.

최종 모습

프론트는 Cloudflare 하나만 바라보고, Cloudflare가 일반 API와 AI VPS를 내부적으로 분기하는 구조가 목표입니다.

이 문서는 “Cloudflare에서 AI API 통신이 안 되는 상황”을 전제로 한 실행 계획서입니다. 다음 단계는 실제 코드 기준으로 프록시 대상 라우트와 인증 전달 방식을 확정하는 것입니다.
