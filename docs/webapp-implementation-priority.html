Webapp Implementation Priority

목적은 다음 goal을 작게 자르는 것입니다. webapp은 Flutter의 핵심 기능을 많이 흡수했지만, 아직 전부는 아닙니다. 따라서 먼저 실데이터 런타임 검증을 하고, 그 다음 핵심 상호작용을 보강하고, 마지막에 진입점과 보조 화면을 정리하는 순서가 맞습니다.

이미 흡수됨: record / calendar / stats / monthly report / sessions 부분 흡수: login / home / report detail / settings / chat 미흡수: onboarding / help / contact / ai hub

원칙

1. 사용자 핵심 흐름부터 한다.
2. Flutter 1:1 복제보다 webapp/PWA 기준의 사용성을 우선한다.
3. backend low-level API는 유지하고 webapp이 app-facing API를 우선 소비한다.
4. 런타임 검증 전에는 Flutter 제거 결정을 하지 않는다.

현재 판단

webapp은 이미 핵심 업무 화면 대부분을 커버한다. 남은 작업은 기능 이식보다 완성도와 진입점 정리에 가깝다.

다음 goal의 범위

한 번에 전체를 잡지 말고 P0, P1, P2처럼 잘라야 한다. 가장 좋은 단위는 실데이터 검증 또는 세션/리포트 상세 보강이다.

P0. 실데이터 런타임 검증

범위 중요도 해야 할 일
로그인 / 세션 최우선 Supabase 세션, bootstrap, active session, logout 흐름을 실제 환경에서 확인한다.
읽기 API 최우선 /api/app/home, /calendar, /record, /stats, /reports/current, /reports, /search를 실데이터로 검증한다.
쓰기 API 최우선 /api/app/chat, /api/app/sessions, /api/app/transactions의 저장/수정/삭제가 DB에 반영되는지 확인한다.
fallback 정책 최우선 guest fallback이 live 경로를 덮지 않고, 비로그인 사용자에게만 제한적으로 동작하는지 확인한다.

P1. 핵심 상호작용 보강

기능 상태 우선 이유
세션 채팅 부분 Flutter의 핵심 상호작용이다. full-screen chat, session sidebar, rename/delete, 메시지 입력 경험을 더 다듬는다.
리포트 상세 CRUD 부분 리포트 생성/조회는 되지만, 이름 변경/저장/삭제의 완성도가 아직 Flutter 수준과 다르다.

P2. 진입점과 계정 화면

기능 상태 메모
로그인 UX 부분 OAuth 정책, 세션 복원, 실패 처리, Kakao 버튼 정책을 정리한다.
온보딩 미흡수 별도 4-step 온보딩이 필요한지 먼저 판단한다. 필요 없으면 로그인/랜딩 카피로 흡수한다.
설정 부분 프로필/구독/로그아웃/약관/문의를 settings route로 둘지, 프로필 카드로 흡수할지 결정한다.

P3. 지원/보조 화면

  • 도움말 별도 help page가 필요한지 판단하고, 필요하면 FAQ와 지원 링크 위주로 최소 구현한다.
  • 문의 contact form을 앱 내부에 유지할지, 외부 폼/지원 채널로 넘길지 결정한다.
  • AI 허브 홈/검색/월간 리포트로 기능이 분산되어 있으면 별도 AI hub는 중복일 수 있다.

P4. 네이티브 대체 후보

아래 항목은 Flutter의 네이티브 기능을 그대로 옮기는 대상이 아니라, webapp/PWA에서 주경로를 최대한 살리고 fallback을 보조로 두는 영역이다.

Ads / interstitial / banner

웹에서는 이 영역을 AdSense 같은 웹 광고 체계로 바꾸는 것이 현실적이다. 다만 core app 화면에 직접 박기보다는 랜딩, 도움말, 콘텐츠 영역, 또는 비핵심 패널에 제한하는 편이 낫다. webapp에서는 광고가 제품 흐름을 방해하지 않도록 별도 정책을 두는 것을 권장한다.

Foreground service / quick entry

이 기능의 주경로는 Web Push Notification + inline reply다. Flutter의 빠른 입력과 가장 비슷한 UX를 web에서 먼저 구현하고, 지원되지 않거나 실패할 때만 fallback을 둔다. Flutter 쪽의 빠른 입력은 flutter_app/lib/native/foreground_service/quick_entry_main.dart, quick_entry_handler.dart, foreground_service_manager.dart처럼 백그라운드 서비스와 MethodChannel에 붙어 있다. 웹에서는 Android Chrome을 1차 지원 대상으로 두고, 미지원 환경이나 실패 시에만 앱 열기 + 미리 채운 입력창으로 fallback한다.

알림 tag / 재표시 정책

tag는 같은 알림을 교체/묶기 위한 식별자이고, renotify는 교체 시 다시 알릴지 여부를 제어한다. 이 둘만으로는 n시간 뒤 재표시를 예약하지 못한다. 재방문 시 다시 보여주려면 앱 상태 저장 후 재노출, 또는 서버/스케줄러 기반 재푸시가 필요하다. 참고로 Chrome 계열에서는 Notification Triggers(showTrigger) 같은 예약 옵션이 있지만, 이 역시 광범위한 브라우저 공통 대체로 보기엔 제한적이다.
정리하면, 이 구간은 “fallback 중심”이 아니라 “inline reply 주경로 + fallback 보조”로 설계해야 한다. 목표 UX가 알림 안에서 바로 기록하는 흐름이므로, webapp은 그 경로를 먼저 만족시키고 보조 경로는 실패 대비로만 둔다.

다음 goal에 대한 권장 방식

1. P0만 목표로 잡는다.
2. P0가 끝나면 런타임 검증 결과를 기준으로 P1로 간다.
3. P1은 세션 채팅과 리포트 상세를 따로 나눌 수 있다.
4. P2/P3는 제품 판단이 섞이므로, 구현 전에 범위를 다시 확인한다.

참조 범위: flutter_app/lib/routes/app_router.dart, flutter_app/lib/features/*, webapp/src/*. 이 문서는 goal 입력용 우선순위 문서이며, 실제 구현은 P0부터 단계적으로 진행하는 것을 전제로 한다.
