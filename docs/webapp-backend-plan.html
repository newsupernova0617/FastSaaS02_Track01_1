Migration Plan

Flutter 대체용 웹앱 + 백엔드 재편 계획

방향은 flutter_app을 점진적으로 웹앱/PWA로 대체하는 것입니다. 다만 Flutter를 당장 걷어내는 전제가 아니므로, 기존 low-level API는 유지하고 그 위에 웹앱용 API를 보강하는 계획으로 갑니다.

1. 목표 구조

최종적으로는 역할을 아래처럼 분리합니다.

영역 역할 비고
frontend/ 랜딩, 블로그, SEO 콘텐츠 Astro SSG 유지
webapp/ 실제 제품 앱, PWA, 설치형 UX Flutter 대체 대상
backend/ 도메인 API 유지 + 웹앱 화면 단위 집계 API 보강 /api/app/* 추가

2. 핵심 판단

1 webapp-preview.ts는 더 이상 런타임 의존이 아님 정리됨

지금 preview 라우트는 UI와 인증이 아직 완전히 붙지 않은 상태에서 화면을 유지하기 위한 fallback입니다.

2 실제 백엔드를 화면 중심 응답으로 보강 Backend

기존 도메인 API는 유지하고, 웹앱이 바로 쓰기 좋은 집계 endpoint를 별도로 둡니다.

3 Flutter 기능을 웹앱 단위로 이식 Webapp

화면, 상태, 인증, 라우팅, 오프라인 캐시를 웹앱 기준으로 재구성하고 Flutter는 점진적으로 역할을 잃게 됩니다.

3. 실행 계획

1 Flutter 기능 인벤토리 작성

먼저 flutter_app/lib 기준으로 기능과 화면을 전부 뽑아야 합니다.

  • 로그인/세션
  • 대화 기록
  • 거래 생성, 수정, 삭제
  • 월별 리포트
  • 검색/질의
  • 설정, 결제, 메모 등 부가 기능
2 백엔드에 앱 전용 API 계층 추가 Backend

추천 경로는 아래와 같습니다.

  • GET /api/app/bootstrap
  • GET /api/app/home
  • GET /api/app/report?month=YYYY-MM
  • GET /api/app/search?q=...
  • GET /api/app/timeline?sessionId=...
  • POST /api/app/chat 또는 세션 기반 메시지 endpoint 정리
3 preview 응답 구조를 실제 계약으로 승격

preview의 장점은 응답이 화면 단위라는 점입니다. 이 형식을 유지하되, 데이터 소스만 실제 DB/서비스로 바꾸는 방식이 좋습니다.

4 webapp을 실제 /api/app/* 우선 사용으로 전환 Webapp

현재 webapp/src/data/preview-api.ts에서 인증 세션이 있으면 /api/app/*를 우선 사용하고, 없으면 preview로 fallback 하도록 바꿉니다.

5 인증/JWT 주입 구조 확정

지금 백엔드의 대부분 /api/*는 인증 전제입니다. 웹앱도 토큰 저장, 재주입, 만료 처리 흐름을 확정해야 합니다.

6 webapp-preview.ts 제거 Cleanup

실제 앱 API와 인증 전환이 끝나면 preview 라우트는 제거하거나 dev-only fixture로 격하합니다.

3-1. 백엔드를 어떻게 바꿀지 상세

핵심은 “기존 API를 버리는 것”이 아니라, 기존 도메인 API 위에 웹앱 화면 단위 API를 추가하는 것입니다. 즉 데이터 모델 중심 응답에서, 화면이 바로 소비할 수 있는 응답으로 한 층 올립니다.

A 라우트 계층을 분리 Backend

추천 구조는 아래와 같습니다.

  • /api/transactions, /api/reports, /api/sessions: 기존 low-level 도메인 API 유지
  • /api/app/bootstrap, /api/app/home, /api/app/report, /api/app/search, /api/app/timeline: 웹앱용 aggregated API 신설
  • 게스트 fallback: 웹앱 내부 mock 데이터로 처리
B 서비스 계층에서 화면용 응답 조립

라우트에서 직접 DB를 여러 번 치고 응답을 손으로 합치기보다, services/app-home.ts, services/app-report.ts 같은 조합 서비스를 두는 편이 낫습니다.

  • 라우트: 입력 검증, 인증, 응답 반환만 담당
  • 서비스: 여러 기존 서비스/쿼리를 묶어서 화면 응답 생성
  • Zod 스키마: 요청/응답 계약을 명시적으로 보장
C Flutter식 기능 단위를 화면 단위 계약으로 치환

Flutter에서는 여러 provider/service가 화면 하나를 구성했을 수 있는데, 웹앱에서는 그걸 프론트가 재조합하지 않도록 백엔드에서 미리 정리해 주는 편이 낫습니다.

3-2. 추천 API 계약

현재 preview 응답 형식을 발전시켜, 실제 앱 계약으로 아래처럼 잡는 것을 권장합니다.

Endpoint 역할 응답 방향
GET /api/app/home 앱 첫 화면 데이터 최근 메시지, 최근 기록 카드, 입력 placeholder, 빠른 상태 요약
GET /api/app/report?month=YYYY-MM 월별 리포트 화면 데이터 총액, 전월 비교, 일자별 추이, 카테고리 집계, 인사이트
GET /api/app/search?q=... 검색/질의 결과 화면 질문, 기간, 총액, 하이라이트 항목, 짧은 해설
POST /api/app/chat 홈 화면 입력창 전송 유저 메시지, 파싱 결과, 생성/수정된 거래, 후속 응답
GET /api/app/timeline 대화/기록 타임라인 조회 메시지와 거래 카드가 섞인 렌더 친화적 리스트

3-3. 각 API가 내부적으로 무엇을 하게 될지

H GET /api/app/home

단순히 메시지 하나를 반환하는 게 아니라, 홈 화면이 바로 렌더되도록 필요한 조각을 같이 줍니다.

  • 최근 사용자 메시지 1~N개
  • 최근 assistant 응답
  • 최근 생성되거나 수정된 거래 카드
  • 오늘/이번주 간단 요약
  • 입력창 placeholder나 추천 질문
R GET /api/app/report

기존 /api/transactions와 /api/reports 결과를 프론트가 다시 조합하지 않도록, 차트 친화적 구조로 정리합니다.

  • 월 총 지출 / 수입 / 순액
  • 전월 대비 증감
  • 일별 시계열 데이터
  • 카테고리별 합계와 비율
  • AI가 만든 짧은 인사이트
S GET /api/app/search

현재 Flutter에서 자연어 질의나 조회 UX가 있다면, 웹앱에서는 질의 결과를 카드 한 장으로 바로 그릴 수 있게 응답을 평탄화하는 편이 좋습니다.

  • 질문 원문
  • 질문이 해석된 기간/카테고리/필터
  • 합계와 평균
  • 세부 항목 요약 리스트
  • 비교 문장 또는 한 줄 인사이트
C POST /api/app/chat

이 endpoint는 결국 홈 화면의 입력창 액션이 됩니다. 그래서 low-level create transaction API보다 화면 반응이 좋아야 합니다.

  • 입력 문장을 파싱
  • 필요하면 AI/규칙 기반 분류 수행
  • 거래 생성 또는 기존 거래 수정
  • assistant 메시지와 거래 카드 DTO를 함께 반환

3-4. 인증은 어떻게 바꿀지

지금의 핵심 문제는 웹앱이 실제 /api/*를 쓰려면 인증/JWT를 안정적으로 붙여야 한다는 점입니다.

  • 웹앱 로그인 후 access token 저장 위치 결정
  • hono/client 또는 fetch wrapper에서 Authorization 헤더 자동 주입
  • 토큰 만료 시 refresh 또는 재로그인 흐름 정의
  • PWA 재실행 시 세션 복원 정책 정리
즉, preview API를 없애려면 단순히 endpoint 이름만 바꾸는 게 아니라 인증과 사용자 컨텍스트를 웹앱 쪽에 정착시켜야 합니다.

3-5. 실제 코드 레벨 변경 예상

영역 예상 변경
backend/src/routes/ app-home.ts, app-report.ts, app-search.ts, app-chat.ts 같은 라우트 추가
backend/src/services/ 기존 transactions, reports, sessions 로직을 묶는 조합 서비스 추가
backend/src/app.ts app.route('/api/app', ...) 마운트, preview 라우트 제거
backend/src/schemas/ 또는 공용 스키마 파일 웹앱 응답 DTO용 Zod 스키마 정리
webapp/src/data/preview-api.ts app-api.ts로 교체, 실제 auth header 주입 포함
webapp/src/lib/query.ts preview query key에서 실제 앱 query key로 변경

3-6. 단계별 전환 순서

1 새 앱 API를 추가한다

기존 API는 건드리지 않고 /api/app/*만 먼저 추가합니다.

2 webapp을 새 API로 바꾼다

홈, 리포트, 검색 화면이 실제 데이터로 렌더되도록 교체합니다.

3 chat/거래 입력을 실제 API로 연결한다

입력창이 더 이상 더미가 아니라 실제 거래 생성/수정 흐름이 되게 만듭니다.

4 preview 라우트를 제거했다

실데이터 전환이 끝나면 기존 webapp-preview.ts는 삭제하고, 현재는 웹앱 내부 mock 데이터만 fallback으로 남깁니다.

4. 파일별 예상 영향 범위

파일/폴더 예상 작업
backend/src/routes/ 앱 전용 집계 라우트 추가 또는 기존 라우트 재정리
backend/src/services/ 화면 단위 응답을 만드는 조합 서비스 추가
backend/src/app.ts preview 라우트 제거, 실제 /api/app/* 라우트 마운트
webapp/src/data/preview-api.ts 실제 앱 API 클라이언트로 전환
webapp/src/data/schemas.ts 실계약에 맞게 요청/응답 스키마 확장
webapp/src/app.tsx 실제 데이터와 상태 전이 반영, placeholder 제거
flutter_app/lib 기능 참조원 역할, 웹 이식 완료 후 축소 또는 제거 대상

5. 우선순위

A 가장 먼저 할 일
  • Flutter 기능 목록 문서화
  • 웹앱 홈/리포트/검색에 대응하는 실제 백엔드 계약 확정
  • 인증 전략 확정
B 그 다음
  • preview 라우트 의존 제거
  • 실제 거래/리포트/검색 데이터 연결
  • PWA 캐시 정책 정교화
주의: 기존 low-level API를 모두 없애는 방향은 비추천입니다. 웹앱용 집계 API를 추가하고, 기존 도메인 API는 유지하는 쪽이 더 안전합니다.
