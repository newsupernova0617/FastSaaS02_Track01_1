Architecture Report

`backend`와 `backend-vps`가 어떤 역할로 나뉘고, 어떤 요청이 어디로 흐르는지 설명하는 구조 보고서

현재 구조는 `backend`를 Cloudflare Workers 메인 게이트웨이로 두고, 직접 AI 통신이 필요한 경로만 `backend-vps`로 프록시하는 하이브리드 백엔드입니다. 두 백엔드는 같은 Turso DB에 직접 접근하지만, 역할 경계는 요청 경로 기준으로 분리되어 있습니다.

역할 분리

핵심은 “일반 API는 Workers”, “직접 AI API는 VPS”입니다.

`backend`가 맡는 것

  • Cloudflare Workers 메인 백엔드
  • JWT 인증, CORS, 로깅, 일반 API 처리
  • `AI_API_BASE_URL` 기준 직접 AI 라우트 프록시
  • 일반 CRUD / 일반 조회 / AI 비직접 경로 처리

`backend-vps`가 맡는 것

  • Node.js VPS에서 실행되는 AI 전용 백엔드
  • LLM 호출
  • 세션 메시지 처리
  • AI 리포트 생성 / 현재 리포트 생성
  • 푸시 응답 기반 AI 처리

공통 전제

  • 둘 다 같은 Turso DB를 직접 사용
  • 둘 다 Supabase JWT를 기준으로 인증
  • 프론트는 Workers 엔드포인트만 알면 됨

요청 흐름

일반 API와 직접 AI API의 요청 흐름은 다릅니다.

sequenceDiagram participant U as User / Frontend participant W as backend (Workers) participant V as backend-vps participant T as Turso participant L as External AI API alt General API U->>W: /api/transactions, /api/users, etc W->>T: direct DB read/write T-->>W: result W-->>U: response else Direct AI API U->>W: /api/ai/action or /api/sessions/:id/messages W->>V: proxy request V->>T: load session / transactions / reports V->>L: LLM request L-->>V: AI response V->>T: save message / save report / update data T-->>V: result V-->>W: response W-->>U: response end

보고서 생성 흐름

`webapp` 사용자가 보고서 작성을 요청하면, 프론트는 Workers만 호출하고 실제 AI 보고서 생성은 `backend-vps`가 담당합니다.

요청 시작점

  • `webapp`이 `backend`로 요청
  • 예: POST /api/reports/generate
  • 또는 POST /api/app/reports/generate

Workers 역할

  • 요청 경로가 직접 AI 라우트인지 판별
  • 해당 경로면 `AI_API_BASE_URL`로 프록시
  • 즉 `backend-vps`로 전달

VPS 역할

  • Turso에서 사용자 거래/기존 리포트 조회
  • 외부 AI API 호출로 리포트 생성
  • 생성 결과를 Turso `reports` 테이블에 저장
sequenceDiagram participant W as webapp participant B as backend (Workers) participant V as backend-vps participant T as Turso participant AI as External AI API W->>B: POST /api/reports/generate B->>V: proxy request V->>T: load user transactions / existing reports T-->>V: source data V->>AI: generate report AI-->>V: report content V->>T: save report T-->>V: saved report V-->>B: response B-->>W: response
중요: `webapp`은 `backend-vps`를 직접 호출하지 않고, 항상 `backend`를 통해 간접적으로 도달

직접 AI 라우트 목록

현재 `backend`가 프록시하고 `backend-vps`가 처리하는 경로는 아래와 같습니다.

레거시 / 세션

  • POST /api/ai/action
  • POST /api/sessions/:sessionId/messages

리포트

Turso 접근 방식

중요한 점은 현재 AI API가 별도 내부 DB API를 거치지 않고, Turso에 직접 붙는다는 것입니다.

현재 방식

  • `backend`도 Turso 직접 접근
  • `backend-vps`도 Turso 직접 접근
  • 즉 DB write 책임이 두 런타임에 분산

장점

  • 구현 단순
  • 프록시 한 번 더 거치는 내부 DB API가 없음
  • AI 처리 후 바로 저장 가능

주의점

  • DB 접근 정책이 두 군데에 존재
  • 권한/검증 로직이 양쪽에서 맞아야 함
  • 장기적으로는 공용 패키지 분리가 더 안전

현재 판단

현재 구조는 “전체 백엔드를 VPS로 옮기지 않고, AI 직접 통신 경로만 VPS로 빼는” 목적에는 잘 맞습니다.

장점

  • Cloudflare를 메인 진입점으로 유지 가능
  • AI 통신 이슈가 있는 구간만 우회 가능
  • 프론트 변경 범위를 최소화 가능

남은 과제

  • `backend-vps`와 `backend`의 중복 코드 관리
  • 프록시 타임아웃 / 재시도 / 로깅 정책 강화
  • 장기적으로 공용 코어 패키지 분리 검토
이 보고서는 2026-05-21 기준 `backend`와 `backend-vps`의 현재 구조를 Mermaid 다이어그램으로 설명하는 문서입니다. 핵심은 “Workers가 메인, VPS가 직접 AI API 전용”이며, 두 런타임이 같은 Turso DB를 직접 사용하는 구조라는 점입니다.
