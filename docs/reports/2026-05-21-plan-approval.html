승인 결정

현재 코드와 문서 기준으로 아래 계획을 승인 대상으로 삼는 것이 합리적입니다.

1. 배포 분리 `backend/`는 Cloudflare Workers 전용, `backend-vps/`는 VPS 전용으로 유지합니다.
2. 직접 AI 오프로드 LLM 호출, 리포트 생성, 세션 메시지 처리 같은 무거운 경로만 `backend-vps`로 보냅니다.
3. Workers 경량화 Workers는 인증, 라우팅, 일반 API, 캐시 가능한 GET 응답, 정적 자산에 집중합니다.
4. Free plan 최적화 정적 자산/캐시/요청 통합으로 Worker 호출 수와 CPU 사용량을 줄입니다.
승인 기준: `webapp`은 계속 `backend`만 바라보고, `backend`는 직접 AI 경로만 `backend-vps`로 프록시한다.

현재 구조

실제 코드는 아래 역할 분리로 동작합니다.

flowchart LR FE[webapp / frontend] W[backend
Cloudflare Workers] V[backend-vps
Node VPS] DB[(Turso)] AI[External AI API] FE --> W W -->|general API| DB W -->|direct AI routes| V V --> DB V --> AI

승인 사유

운영 안정성

Cloudflare에서 AI 통신 이슈가 있을 때, Workers 전체를 내리지 않고 문제 경로만 우회할 수 있습니다.

CPU 완화

10ms CPU 제한을 넘기기 쉬운 AI/리포트 경로를 VPS로 이동시키면 Workers는 가벼운 게이트웨이로 유지됩니다.

호출 절감

정적 자산, 캐시, 요청 통합으로 Workers invocation을 줄일 수 있습니다.

승인 조건

승인이 끝나면 아래 조건을 기준으로 유지/검증합니다.

구조 조건

  • `backend`는 Workers 전용
  • `backend-vps`는 AI 전용
  • `webapp`은 Workers만 호출

성능 조건

  • Workers에서 큰 JSON 파싱/가공을 최소화
  • 자주 읽는 응답은 캐시
  • 정적 파일은 Worker를 타지 않게 처리

검증 조건

  • `backend`와 `backend-vps` 각각 type-check 통과
  • Workers dry-run 통과
  • 보고서 흐름과 배포 경계 문서 일치
주의: 현재 `backend-vps`는 Turso에 직접 접근한다. 이건 승인된 설계지만, 장기적으로는 공용 코어 패키지 분리가 더 낫다.
