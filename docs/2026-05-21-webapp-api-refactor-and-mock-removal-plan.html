Refactor Plan

preview-api.ts 실제 API 계층 전환 + mock fallback 제거 계획

이 문서는 docs/webapp-backend-plan.html의 방향을 실제 코드 수준으로 내린 계획입니다. 핵심은 preview-api.ts를 더 이상 preview 중심 파일로 두지 않고, 실제 /api/app/* 계약을 쓰는 앱 API 계층으로 바꾸는 것입니다.

현재 파일
preview-api.ts
목표 파일
app-api.ts
제거 대상
mock-data.ts
실제 API 우선이 아니라 실제 API 전용으로 전환 query 계층도 preview 명칭 제거 런타임 fallback 삭제

1. 현재 구조 진단

현재 webapp/src/data/preview-api.ts는 이름과 다르게 두 역할을 동시에 하고 있습니다.

  • 실제 /api/app/* 호출
  • 실패 시 mock-data.ts fallback
이 구조는 전환기에는 유용했지만, 실제 앱 계약이 생긴 지금은 책임이 섞여 있습니다. 파일 이름도 현재 역할을 정확히 설명하지 못합니다.

2. 리팩토링 목표

1 preview 개념을 런타임 데이터 계층에서 제거

읽기 화면도 실제 API만 호출하도록 바꿉니다. 실패 시 mock을 반환하지 않고 에러를 그대로 surface 합니다.

2 preview-api.ts를 app-api.ts로 치환

앱이 실제로 쓰는 계층이라는 점을 파일명과 함수명에 반영합니다.

3 query key와 query function 명칭도 실제 API 기준으로 정리

현재 preview 키를 쓰는 query cache 이름도 앱 계약 기준으로 바꿉니다.

4 mock 데이터는 런타임 코드에서 제거

필요하면 fixture/test data로만 남기고, 제품 코드에서 import 하지 않도록 정리합니다.

4. 실제 코드 리팩토링 방향

A 공통 fetch wrapper를 명시적 에러 방식으로 변경

현재 fetchWithOptionalAuth()는 토큰이 없거나 401/403이면 null을 반환합니다. 실제 API 계층에서는 이걸 숨기지 말고 에러나 인증 상태로 분리하는 편이 낫습니다.

  • Missing auth token
  • Unauthorized
  • Forbidden
  • Request failed with status ...
B 읽기 API도 전부 실제 함수명으로 정리

preview 접두사는 더 이상 맞지 않습니다. 함수명만 봐도 백엔드 엔드포인트가 드러나야 합니다.

C 쓰기 API와 읽기 API의 반환 패턴 통일

지금은 어떤 함수는 null, 어떤 함수는 SourcedData를 돌려줍니다. 목표 구조에서는 전부 parse된 DTO를 반환하고 실패는 예외로 다룹니다.

7. query 계층 변경 계획

현재 webapp/src/lib/query.ts는 query key와 query function에 모두 preview 개념이 들어가 있습니다.

  • ['preview', 'home'] → ['app', 'home']
  • ['preview', 'report', month] → ['app', 'report', month]
  • ['preview', 'calendar', month, date] → ['app', 'calendar', month, date]
query key는 캐시 키이기도 하지만, 이 프로젝트에서는 아키텍처 용어를 코드에 고정하는 역할도 합니다. 제품 앱이 된 이상 preview라는 용어를 계속 남기는 건 좋지 않습니다.

8. mock fallback 완전 삭제 계획

1 읽기 화면 API 100% 실백엔드 계약 확인

home, report, search, calendar, stats, reports/current의 실제 응답이 모두 프론트 스키마와 일치하는지 검증합니다.

2 preview 함수 제거

fetch*Preview() 계열을 제거하고, query layer는 실제 API 함수만 사용하도록 바꿉니다.

3 SourcedData 제거

화면에서 source: 'live' | 'preview'를 신경 쓸 필요가 없어집니다. DTO만 받도록 단순화합니다.

4 mock-data.ts import 제거

제품 코드 어디에서도 mock-data.ts를 참조하지 않게 만든 뒤 파일 삭제 여부를 결정합니다.

5 에러 화면/로딩 화면을 실제 API 실패 중심으로 재정의

fallback으로 화면을 채우지 않으므로, 인증 실패와 서버 실패를 UI에서 분명하게 보여줘야 합니다.

9. 삭제 전 체크리스트

항목 체크 기준
/api/app/home 게스트가 아닌 로그인 사용자 기준으로 항상 정상 응답
/api/app/report 빈 거래 데이터에서도 프론트 스키마 만족
/api/app/search 검색 결과 0건일 때도 계약 유지
/api/app/calendar 월별 거래 0건일 때 days/selectedDay 구조 유지
/api/app/stats 카테고리/리포트 없을 때도 빈 배열 계약 유지
/api/app/reports/current 월간/주간 둘 다 실제 응답 가능
인증 흐름 토큰 누락/만료 시 UI가 mock으로 숨기지 않고 오류 처리

10. 실제 작업 순서

1 app-api.ts 신규 작성

기존 preview-api.ts를 복사하지 말고, 실제 API 전용 구조로 새 파일을 만듭니다.

2 query.ts를 새 함수들로 연결

query key와 query function을 전부 교체합니다.

3 main.tsx import 정리

현재 preview-api.ts import를 app-api.ts로 바꿉니다.

4 SourcedData 의존 제거

화면 컴포넌트와 observer 타입에서 preview source 메타를 걷어냅니다.

5 mock-data.ts 삭제 또는 test fixture로 이동

런타임 import가 0이 되면 삭제합니다. 유지가 필요하면 tests/fixtures 성격으로 옮깁니다.

11. 결론

  • preview-api.ts는 이름부터 실제 역할과 어긋납니다. 새 이름의 실제 API 계층으로 갈아타는 게 맞습니다.
  • fallback mock은 전환기 안전장치였지만, 제품 앱 구조로는 오히려 오류를 숨기고 상태를 복잡하게 만듭니다.
  • 삭제 순서는 “실백엔드 계약 확인 → query 전환 → source 메타 제거 → mock 제거”가 안전합니다.
