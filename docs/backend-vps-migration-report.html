Backend VPS Migration Report

백엔드는 VPS로 옮기고, 프론트는 Cloudflare Pages에 남기는 구성이 맞다

현재 문제는 Cloudflare에서 나가는 요청이 provider 쪽 지역/egress 정책에 걸릴 가능성이다. 이 경우 Pages Functions나 Workers 안에서 provider를 바꿔도 근본 원인이 그대로 남을 수 있다. 가장 안전한 분리는 backend만 VPS로 옮기고, frontend는 정적 호스팅으로 유지하는 것이다.

Frontend: Cloudflare Pages 유지 Backend: VPS 이전 권장 Cloudflare egress 종속 제거

구현 상태

VPS 진입점 추가
backend에 src/server.ts를 넣고, tsx 기반 start:vps / dev:vps 스크립트를 추가했다. 같은 Hono 앱을 Node 서버로 띄울 수 있다.
Turso vector로 RAG 이관
Cloudflare Vectorize 의존을 걷고, user_notes / knowledge_base에 Turso vector 컬럼과 인덱스를 붙였다. RAG는 Turso vector를 기본 경로로 쓴다.
AI provider 우선순위 반영
기본값은 AI Studio/Gemini, 그다음 OpenRouter, 마지막 OpenAI로 둔다. Cloudflare Workers AI는 Cloudflare 전용 fallback으로 남겼다.

왜 이 구성이 맞나

Cloudflare Pages는 프론트에 잘 맞음
현재 frontend는 랜딩/블로그용 Astro SSG라서 Pages와 잘 맞는다. 정적 자산만 서빙하면 운영이 단순하고 배포도 가볍다.
backend는 네트워크 종속이 많음
AI 호출, 벡터 검색, 푸시, Google Play 연동 등 외부 API 의존이 많다. Cloudflare egress를 거치면 provider가 국가/소스 IP를 이유로 거절할 수 있다.
Pages Functions는 여전히 Cloudflare 네트워크 안
Functions는 Cloudflare 네트워크에서 실행되는 server-side 코드다. backend를 Pages Functions로 옮기면 egress 문제를 완전히 피하지 못한다.
VPS는 호출 경로를 직접 제어 가능
VPS에서 OpenAI / Gemini / OpenRouter로 직접 나가면 Cloudflare egress에 묶이지 않는다. provider fallback, proxy, retry도 서버에서 단순하게 설계할 수 있다.

현 코드 기준으로 옮겨야 할 것

backend/src/services/llm.ts backend/src/services/vectorize.ts backend/src/routes/ai.ts backend/src/routes/app.ts backend/src/routes/reports.ts backend/src/routes/push.ts backend/src/services/session-message-handler.ts backend/src/services/google-play-billing.ts backend/src/services/push.ts backend/src/services/ai-report.ts

VPS로 이동할 핵심

  • AI provider 호출: AI Studio를 기본값으로 두고, OpenRouter와 OpenAI를 fallback으로 둔다.
  • Vector search / RAG 계층: Cloudflare Vectorize 대신 Turso vector로 옮긴다.
  • session-message-handler와 report 생성 라우트: 사용자 입력을 AI/DB로 해석하고 리포트를 만드는 핵심 경로다.
  • web push, quick entry, Google Play RTDN: 알림, 즉시입력, 구독 동기화 같은 운영 경로다.

Cloudflare에 남길 수 있는 것

  • frontend 정적 호스팅: Cloudflare Pages
  • 선택 사항: Pages의 단순 리디렉션 / 정적 form / CDN
  • 장기적으로는 backend 프록시를 끊는 것이 더 깔끔함

AI provider 우선순위 제안

백엔드가 VPS로 이동한다면 provider 호출은 더 단순하게 정리하는 편이 좋다. 권장은 AI Studio 기본, OpenRouter fallback, OpenAI fallback 순서다.

1. AI Studio를 기본값으로 둔다
Gemini 계열 모델을 가장 먼저 시도한다. 이미 AI Studio를 쓰고 있고, 모델 품질과 가격을 유지하기 쉽다.
2. OpenRouter를 fallback으로 둔다
특정 provider가 지역/egress 정책으로 막힐 때 우회용으로 좋다. 다만 플랫폼 수수료가 추가될 수 있다.
3. OpenAI를 마지막 fallback으로 둔다
응답 품질이 안정적이고 OpenAI 호환 호출이 쉬우므로, AI Studio가 막히면 비교적 깔끔한 대체안이 된다.
4. Cloudflare Workers AI는 제거 후보
Cloudflare egress와 묶이는 경로이므로, 이번 문제를 정면으로 피하려면 backend VPS에서 직접 호출하는 쪽이 낫다.

Vector search / RAG 마이그레이션: Turso vector 확정

지금 backend는 이미 Turso/libSQL을 쓰고 있다. 그래서 Vector / RAG는 별도 벡터 DB를 새로 두기보다 Turso vector로 붙이는 게 가장 자연스럽다. Cloudflare Vectorize는 빼고, 같은 DB 계열 안에서 벡터 검색을 처리하는 쪽으로 간다.

1순위: Turso vector
현재 DB가 Turso이므로 이 프로젝트와 가장 잘 맞는다. 관계형 데이터와 벡터를 같은 운영 단위에서 다루기 쉬워서 변경량이 적다.
2순위: Postgres + pgvector
backend를 Turso에서 완전히 떼어내는 시점이 오면 가장 정석적인 대안이다. 다만 지금 단계에선 DB 자체를 바꾸는 비용이 크다.
3순위: Qdrant / managed vector DB
RAG 규모가 커지거나 벡터 기능이 더 강하게 필요할 때 고려한다. 지금 단계에서는 운영 복잡도와 외부 의존이 늘어난다.
비추천: Cloudflare Vectorize 유지
backend를 VPS로 옮기는 목적이 Cloudflare egress 분리라면, Vectorize만 Cloudflare에 남기는 건 구조상 덜 깔끔하다.
권장안: 1) 현재 backend + Turso vector 2) backend를 VPS로 옮겨도 Turso vector 유지 3) RAG 규모가 커지면 pgvector 또는 Qdrant 재검토

생소할 수 있는 서비스들

session-message-handler
사용자가 홈 채팅이나 quick entry로 문장을 보내면, 이 서비스가 그 문장을 받아 AI에 해석시키고 거래 생성 / 수정 / 삭제 / 보고서 요청 / 단순 대화로 분기한다. 사실상 이 앱의 "대화 인입부"다.
report 생성 라우트
월간/주간 리포트, 저장된 리포트 목록, 리포트 상세 조회/수정/삭제를 담당한다. 숫자 집계와 화면용 요약을 묶어 반환한다.
web push
브라우저가 지원하는 푸시 알림이다. 앱을 열지 않아도 알림을 보낼 수 있고, quick entry의 입구가 된다.
quick entry
알림에서 바로 "오늘 커피 4500원" 같은 문장을 넣어 기록하는 기능이다. 네이티브 Flutter에서 하던 빠른 입력 UX를 PWA 쪽에서 최대한 재현하려는 것이다.
Google Play RTDN
Google Play가 구독/결제 상태 변화를 서버로 알려주는 실시간 알림이다. backend가 이 신호를 받아 구독 만료, 갱신, 취소를 동기화한다.
왜 VPS로 옮겨도 남나
이 기능들은 Cloudflare 전용이 아니라 비즈니스 로직이다. 서버 위치만 VPS로 바뀌어도 웹푸시, 구독 동기화, 리포트 생성은 그대로 필요하다.

유지 / 이관 / 제거 판단

session-message-handler → 유지, VPS로 이관 필수 report 생성 라우트 → 유지, VPS로 이관 web push → 유지, PWA quick entry용 quick entry → 유지, PWA 핵심 UX Google Play RTDN → 조건부 유지, Play 구독을 계속 쓸 때만 필요 Cloudflare Workers AI → 제거 후보, egress 문제를 피하려면 VPS 직접 호출로 대체 Cloudflare Vectorize → 제거 후보, Turso vector / pgvector / Qdrant로 대체

추천 마이그레이션 순서

1. backend API 서버를 VPS에 올린다
Hono 기반 Node 서버를 그대로 유지하고 DB 연결만 VPS에서 처리한다. 프론트의 API base URL만 바꾸면 된다.
2. AI 호출을 VPS에서 직접 나가게 바꾼다
Cloudflare Workers AI와 Pages Functions 경로를 끊고, OpenAI / Gemini / OpenRouter를 VPS에서 직접 호출한다.
3. 벡터 검색과 파일 없는 상태를 정리한다
Cloudflare Vectorize 의존을 유지할지, pgvector / Qdrant / Pinecone / 자체 Postgres로 옮길지 결정해야 한다.
4. frontend는 Pages 유지
랜딩과 블로그는 계속 Pages에서 제공하고, API만 VPS로 분리하면 배포 복잡도가 과도하게 올라가지 않는다.

주의할 점

Pages Functions에 AI를 남기지 말 것 Cloudflare Vectorize는 대체 필요할 수 있음 CORS / auth / session token 재정의 필요 frontend는 그대로 유지 가능
  • Cloudflare AI Gateway는 관리층이지, egress 출발점을 바꾸는 해결책은 아니다.
  • OpenRouter는 provider fallback으로 유효하지만, 최종적으로는 VPS에서 직접 호출하는 편이 단순하다.
  • 2vCPU / 12GB VPS는 이 앱의 현재 구조상 충분할 가능성이 높다. 병목은 연산보다 외부 API I/O와 DB 왕복에 있다.

결론

이 프로젝트는 frontend는 Cloudflare Pages, backend는 VPS로 나누는 하이브리드 구조가 맞다. 지금의 Cloudflare egress 문제를 가장 깔끔하게 끊는 방법이고, AI provider 전환도 그 위에서 더 단순해진다.

참고: Cloudflare Pages Functions는 Cloudflare 네트워크 안에서 실행되며, Cloudflare의 기본 egress IP는 공유 주소 공간이다. Pages Functions, Cloudflare IP addresses, Dedicated egress IPs
